# release

Kit root (`<KIT>` in shared files and agents): `${CLAUDE_SKILL_DIR}/../core`. Include `Kit root: ${CLAUDE_SKILL_DIR}/../core` in the prompt of every agent you spawn. Work from the project root (`${CLAUDE_PROJECT_DIR}`) and do not `cd` away from it.

Input: $ARGUMENTS
State: !`python3 -I "${CLAUDE_SKILL_DIR}/../core/scripts/dev_state.py" --root "${CLAUDE_PROJECT_DIR}" status`

Let `DS` = `python3 -I "${CLAUDE_SKILL_DIR}/../core/scripts/dev_state.py" --root "${CLAUDE_PROJECT_DIR}"` and `SC` = `python3 -I "${CLAUDE_SKILL_DIR}/../core/scripts/dev_score.py"`.

## Planned releases (conventions.md §19)
Every release is planned since 3.0. Read `lifecycle.release` from `DS status --json`. When `release` (an id such as `R2`) is null, the plan has no `## R<n>` yet: run `DS sync-plan` (it groups an older plan into releases) and stop with `/dev-kit:review plan`. Otherwise its `status` decides what this run does:
- `in_progress`: stop and say which milestones of the release are still open (`waiting_for`); nothing is released half built.
- `ready_for_review`: run steps 1–5, then step **D** (release review) and stop. Steps 6–8 wait for the approval.
- `awaiting_approval`: the decision belongs to the user. With `--approve` or `--reject "<feedback>"` in the input, record it; otherwise show the release review's path and its summary and ask (AskUserQuestion): "Approve <R> for production?" with the options Approve and Reject (a rejection asks next for what must change, one item per line). Record it with `DS release-decide <R> --approve`, or `DS release-decide <R> --reject --feedback "<item>"` with one `--feedback` per item. Approved → go on with steps 6–8 now. Rejected → report the fixes milestone it created and stop; its last line is `/dev-kit:implement`.
- `deploying_prod` (approved): run steps 6–8 only. Steps 1–5 ran for this candidate before it was submitted; if a commit landed outside `.dev/` since the submission, stop and submit again (steps 1–5 and D).
The approval is also the confirmation of `pause_policy.production_deploy` for the approved commit: step 8 does not ask again. Every other pause point stays as configured (§10).

## Checklist (stop at the first failure and say what is missing)
Log `skill_start`/`skill_end` (`conventions.md` §13; the plugin hooks log the agents); give each auditor a `Slot: N` and the isolation line, and run `DS cleanup` after them.
1. Next release (`conventions.md` §19), from `DS status --json` → `lifecycle.release`: `milestones` (closed since the last release, or the closed milestones of the planned release) is not empty, otherwise stop ("nothing to release"); `waiting_for` is empty and no task is `in_progress`, so the tag never takes a milestone half built (finish it, or release after its gate); every gate of those milestones `passed` (with its score) or `skipped`/forced with an ADR; reviews `prd`, `design` (UI products) and `plan` are `pass` or `n/a`; `usability` and `docs` are `done` or `n/a`, which means review `ux` (UI products) and review `docs` passed after the last of those milestones (run `usability`, or `docs` then `review docs`, when one says `todo` or `review`). Working tree clean outside `.dev/` (`git status --short -- . ':(exclude).dev'`).
2. Run the full test suite, lint and type-check; run the build command from `architecture.md`.
3. Secrets hygiene: run the detection commands in `${CLAUDE_SKILL_DIR}/../core/shared/checklists/security-secrets.md`; `.env.example` complete.
4. Release audit with score: spawn in parallel `spec-tracer`, `security-auditor`, `ops-reviewer`, `deps-auditor`, `data-reviewer` (if there is a database), `performance-auditor` and `docs-reviewer`, all with scope `release` (existing projects: also `Baseline: <brownfield.baseline_ref>`, so they audit only `git diff <baseline_ref>..HEAD` and mark untouched legacy problems `"legacy": true`). This audit is the full sweep of `conventions.md` §18: no ledger reuse (every `ledger plan` with `--no-cache`, no `Files to review:` list, no carried result; the shared baseline is built fresh on the release commit). Pass `model` and `effort` in every Agent call (`conventions.md` §9) and give each `Output file: .dev/qa/release/raw/<agent>.json`; run `SC check --fix` on those files (missing or invalid → as in `qa` §3.1), then score with `python3 -I "${CLAUDE_SKILL_DIR}/../core/scripts/dev_score.py" score --scope release --kind gate --root . --out .dev/qa/release/scores.json .dev/qa/release/raw/*.json`. Require exit 0 (no blocking findings, every dimension and the overall score at or above the cut-offs); every must-have AC must be `complete`. Legacy findings (`scores.json` → `legacy`) become issues as in `qa` §4, never fix tasks. On failure consolidate the findings into `.dev/qa/release/findings.json`, challenge each critical/high as `qa` §4 does (`DS challenger release <F-id>`, `DS challenge record release --from …`, then score and consolidate again with `--challenges .dev/qa/release/challenges.json`), and create the fix tasks with `DS fix-tasks --from .dev/qa/release/findings.json --milestone <last milestone> --source qa/release/report.md`; under `autopilot` return to `implement` and re-run `release` (rounds as in `qa`); otherwise stop and tell the user to run `implement` then `release` again.
5. Docs: README, CHANGELOG present and no fragment left in `changelog.d/` or `docs/setup.d/` (run `docs` first if not; it merges them); open questions reviewed — list the still-open ones in the release notes as known limitations.
D. Planned release only — the release review: write `.dev/releases/<R>/review.md` from `${CLAUDE_SKILL_DIR}/../core/shared/templates/release-review.md` (ACs from the spec-tracer output of step 4, gate scores from `DS status --json`, scores of step 4, smoke results, the local preview link and the screenshots of the main flows when there are some). Then `DS release-submit <R> --review .dev/releases/<R>/review.md`, report the release review's summary and stop: the board shows the release in Needs you with Approve and Reject, and the chat decides by running `/dev-kit:release` again. Under `autopilot` this is where the run stops; it never approves.
6. Version: from the argument or next semver per brief (breaking → major, features → minor, fixes → patch). Update version files (package.json / pyproject / Cargo.toml …), CHANGELOG heading with date, and write `.dev/release-notes-<version>.md` from `${CLAUDE_SKILL_DIR}/../core/shared/templates/release-notes.md`.
7. Commit `chore(release): v<version>` and tag `v<version>` (annotated). Push and publish only if `autonomy.may_push` is true and the brief's block 9 asked for it; deploying anywhere public is `public_exposure` → ask first unless already authorised in the brief or `pause_policy.public_exposure` preauthorizes that target; `park` → stop after tagging and list the deploy as pending.
Before `skill_end`, run `python3 -I "${CLAUDE_SKILL_DIR}/../core/scripts/dev_cost.py" --root "${CLAUDE_PROJECT_DIR}" ingest` (token usage per stage, `conventions.md` §14).
8. If `autonomy.production.when` is `on_release`, run `deploy` for the tagged commit (it asks or parks per `pause_policy.production_deploy`). If a local preview is running (`conventions.md` §11), replace it with the released version when `local_deploy.mode` is `keep_running`, otherwise stop it. With release flags on (`conventions.md` §12, `DS flag list --json`), the approved release is already in production behind `release_R<n>`: turn the flag on there with the mechanism of `architecture.md` §7, run the production smoke checks (a failure: turn it off again, `DS flag set release_R<n> off --rollback`, and stop), record `DS flag set release_R<n> on`, then record the release; `release-record` adds the chore that removes the flag to the next release. Otherwise, for a planned release, deploy to production when the project has one (`production.when` is `on_release` or `per_milestone`; with `manual`, list it as pending) and run the production smoke checks of `deploy`; a failed smoke stops here with the rollback `deploy` reports, and the release is not recorded. Record the release: `DS release-record --version <version> --tag <tag> --release <R>` (refused before its approval; with nothing open the project is `stable`). If the next release was built ahead (`DS pipeline status --json` → `branches` has `dev-kit/R<n+1>`), integrate it: `DS pipeline integrate dev-kit/R<n+1>` rebases it on the main branch, invalidates the ledger of the files the rebase changed, sends its gated milestones back to `qa` on the delta, and fast-forwards; a conflict becomes a question in Needs you. Report: version, tag, release score vs cut-off, scores of every gate and review, verification summary, known limitations, and how to run/deploy.

`--hotfix`: patch release for a closed hotfix (`conventions.md` §15): skip step 1's next-release check; require the hotfix task `done`, its scoped QA passed (review `hotfix-<task>` is `pass` in `DS status --json` → `reviews`; `qa --scope <task>` records it) and the suite green; bump only the patch number; CHANGELOG entry under "Fixed" with the issue id; tag; then step 8 deploys it once and records it with `DS release-record --version <version> --tag <tag> --hotfix <task>` (it ships no milestone; what waits for the next release stays as it was) (per `pause_policy.production_deploy`) when there is production. Nobody deploys the hotfix before this step.

`--dry-run`: perform steps 1–5 and report what would happen in 6–8 without changing anything.

**Last line** (`conventions.md` §15): end the final report with the next command alone on the last line, written in full: `/dev-kit:release` after a submission (the decision), `/dev-kit:implement` after a rejection, `/dev-kit:deploy` when production waits for it, otherwise `/dev-kit:backlog`. Claude Code then offers it as the greyed-out prompt suggestion (Tab or Right arrow).

## Existing projects (brownfield)

When state has `brownfield` (`conventions.md` §16):
- Step 1: a review recorded as `n/a` counts as passed; `existing` ACs count as complete when `spec-tracer` reports them `existing-verified`. In `maintenance` mode the next release holds the closed maintenance milestones.
- Step 6: the current version comes from the manifest named in `.dev/discovery.md` §11 and the latest tag; bump from there (never restart at 0.1.0). If manifest and tag disagree, ask which one is right. Keep the project's CHANGELOG format.
- Step 7: commit with `autonomy.commit_style` (e.g. `chore(release): 2.4.0`) and tag with the project's prefix (`v2.4.0`, `2.4.0`, `release-2.4.0`).
- Step 8: with `production.method` `external`, the project's pipeline deploys the tag; `deploy` only records it.
