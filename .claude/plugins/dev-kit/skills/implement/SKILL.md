# implement

Kit root (`<KIT>` in shared files and agents): `${CLAUDE_SKILL_DIR}/../core`. Include `Kit root: ${CLAUDE_SKILL_DIR}/../core` in the prompt of every agent you spawn. Work from the project root (`${CLAUDE_PROJECT_DIR}`) and do not `cd` away from it.

Input: $ARGUMENTS
State: !`python3 -I "${CLAUDE_SKILL_DIR}/../core/scripts/dev_state.py" --root "${CLAUDE_PROJECT_DIR}" status --short --quiet-if-missing`
Git: !`git status --short 2>/dev/null | head -20`

Let `DS` = `python3 -I "${CLAUDE_SKILL_DIR}/../core/scripts/dev_state.py" --root "${CLAUDE_PROJECT_DIR}"`.

## Setup (once per run)
1. Read `${CLAUDE_SKILL_DIR}/../core/shared/conventions.md` (§5 commits, §6 autonomy), `${CLAUDE_SKILL_DIR}/../core/shared/checklists/test-pyramid.md`, `.dev/architecture.md`, `.dev/decisions.md`; keep `.dev/design/*.md` and `.dev/prd.md` at hand for the tasks touched. Load the autonomy policy from `DS status --json`.
2. Reconcile: if the working tree has uncommitted changes that belong to an `in_progress` task, continue that task. If they belong to nothing known, apply `pause_policy.dirty_tree` (`conventions.md` §10): `ask` → stop and ask what to do; `auto_recommend` → `git stash push -u -m "dev-kit auto <date>" -- . ':(exclude).dev'` and log it (never stash `.dev/`, `conventions.md` §5). Never commit unknown changes.
3. Parse arguments: a specific task id; `--tasks N` (default: until the current milestone's tasks are all done); `--milestone Mn`; `--parallel N` (use `implementer` agents for independent ready tasks, max N); `--skip-gate` (writes an ADR `(user)` and runs `DS gate <prev> skipped`).

## Loop per task
Hotfix tasks (`lane: hotfix`, `conventions.md` §15) come first from `DS next`, even with a pending gate; only one is open at a time. When a hotfix is done, the next step is `qa --scope <task>`, then `release --hotfix` (which deploys it when there is production). Cool-down tasks (`lane: cooldown`) come next. End the run report with one tip from `DS tip implement`.
Log `skill_start`/`skill_end` once per run (`conventions.md` §13); the task transitions are logged by `dev_state.py` itself.
1. `DS next [--milestone Mn] --json` → if exit code 3, read the reason: milestone complete → stop and say "run `qa <M>`" (continue into `qa` when invoked by `autopilot`); gate pending → stop unless `--skip-gate`; only blocked tasks → report them and stop.
2. `DS start T-xxx` (it records the task's tier and route and prints them: `· opus / high (quality)`). `DS brief T-xxx` prints the task with its languages, commands, verification rule, any `Previous attempt` from the ledger (a task blocked earlier or reopened by a fix keeps its branch and notes: continue from them instead of starting over) and the `Tier:`/`Route:` lines (`conventions.md` §9 "Tier per task" and "Router"). **Who implements it:** a task routed to `speed` or `quality` (haiku or opus) is delegated to one `implementer` with that `model` and `effort`, exactly as in `--parallel` with N = 1 (worktree, brief as the prompt, integration and commit by you); a `balanced` or `balanced+` task is done inline, and for `balanced+` you work with high care: cross-check every file of the task and every AC before the commit. Applying the route is not an escalation and needs no consent. Read the task's acceptance, test_notes, files; read the relevant spec sections and the existing code you will touch (reuse utilities; follow architecture layout).
3. Tests first: write failing tests per AC (name/comment with `AC-n`), then implement until green. Run the **full** suite plus lint/type-check. Fix regressions you caused.
3a. Accumulating files and shared resources: write the task's CHANGELOG entry to `changelog.d/T-xxx.md` (setup notes to `docs/setup.d/T-xxx.md`) instead of editing `CHANGELOG.md` or `README.md`; use the message catalog of `ux-flows.md` §7.1 for validation and status texts; take `DS lock acquire <resource> --holder <you>` before using a resource listed as exclusive in `architecture.md` §7 and `DS lock release` after.
3b. Self-check and task checks (before the commit; the gate then confirms instead of discovering): run the implementer's self-check (`agents/implementer.md` step 4a: AC ↔ test, copy, static a11y on what you touched). Then, per `autonomy.task_checks` (default `ui`): when the task touches UI files (components, templates, styles, string catalogs; with `all`, any task with user-facing strings), spawn `copy-reviewer` (`model: sonnet`) and `a11y-auditor` (`model: haiku`) with `Mode: static`, scope `T-xxx`, `effort: medium`, `Output file: .dev/qa/T-xxx/precheck/<agent>.json`, in parallel and in the background. Fix their critical/high findings inside the task and re-run the suite; medium and low go into the commit body as known. `off` skips the agents, not the self-check.
4. Decisions: apply the autonomy rule. `decide_alone` → decide, append `ADR-nnn (auto)` to `.dev/decisions.md`, optionally `DS add-question`. `always_ask` → first apply the category's `pause_policy` action (`conventions.md` §10: `preauthorize` within its limit, `auto_recommend`, or `park`); only for `ask`: if running under `autopilot` and the task can be finished without the answer, finish it with the safest assumption and queue the question; otherwise `DS block T-xxx --reason "needs decision: ..."` and ask the user with AskUserQuestion (recommended option first), then `DS unblock` and continue.
5. Time budget: if the task is not converging after roughly `task_time_budget_min` of effort (many failed attempts, environment problems), keep the partial work on a branch (`git stash`-free: commit it to `dev-kit/T-xxx` from a worktree or leave the implementer's worktree branch), record it with `DS ledger put task:T-xxx --result failed --note "<what was tried, what failed>" --ref <branch>`, then `DS block T-xxx --reason "<concrete blocker>"`, write what you tried in `.dev/log.md` via the block reason, and move to the next ready task.
6. Commit (when `commit_per_task` is true; if a hook rejects it, fix and retry, and only then take the SHA): `git add` only the task's files (and lockfiles/config it legitimately changed) plus the tracked `.dev/` files (state, plan, decisions, log of the previous step); subject from `autonomy.commit_style` (default `[T-xxx] <type>: <summary>`; trailer `Refs: T-xxx` when the template has no `{task}`, `conventions.md` §5): `git commit -m "<subject>" -m "<body: what, ACs, how verified>"`. Then `DS done T-xxx --commit $(git rev-parse HEAD)` and record the green suite you ran on that code: `DS tests record --kind all --passed <n> --failed 0 --command "<test command>" --duration <s>` (add `--coverage <pct>` when measured), so the test auditor and the gate reuse it instead of running it again. If committing is disabled, just `DS done T-xxx`.
7. One-line progress note to the user (task, tests count, commit short SHA). Repeat.

## `--parallel N`
Pick the batch with `DS next --batch N --json`: up to N ready tasks with no file in common and at most one that touches a serialising file (manifests, lockfiles, migrations, registries, barrels, CHANGELOG/README, or `shared` in the plan). **Serialize** (never run two at once) tasks that touch shared files: route/registry indexes, package `__init__`/barrel files, the migrations head (any task that adds a migration), lockfiles and manifests, shared config.
- Spawn one `implementer` per task with the Agent tool, `run_in_background: true`, the `model` and `effort` of its route (`DS tier T-xxx --json` → `final_model`, `final_effort`; `conventions.md` §9; pass them explicitly, and add `tier` and `risk_score` to its `agent_spawn`/`agent_end`) and **`isolation: "worktree"`**, so each works in its own git worktree; set the Agent `description` to `T-xxx <short title>` and give each the output of `DS brief T-xxx` as the base of its prompt (task, the `Scope: T-xxx` line the board links by, languages, commands, the verification rule: unit, lint, type-check and only the integration tests it affects), the task id, the language, `Project root: ${CLAUDE_PROJECT_DIR}` (it runs `dev_state.py --root` on it from its worktree), a distinct `Slot: N` and the isolation line (`resource-isolation.md`: own port, database, scratch folder and PIDs). `DS start` each with `--force`. Log `agent_spawn`/`agent_end` (`conventions.md` §13).
- When a report arrives, integrate **one at a time** in the main checkout: merge the worktree's branch (on conflict, log `error code=merge_conflict` and re-run that task alone after the others), run the full suite and the type-check yourself, review the diff briefly, commit (hooks run only here, sequentially), `DS done` and `DS tests record` for that run. If a hook rejects the commit, fix and commit again, then record the SHA of the commit that landed (`git rev-parse HEAD` after it succeeds).
- `needs_decision` → handle per step 4; `blocked` → `DS block` (the router counts it: two failures in a row in one context raise it one tier for the rest of the milestone, and `DS block` says so). A `spec_deviation` in the report → update the spec file or create a fix task, never leave spec and code silently apart.
- After each batch run `DS cleanup`. Keep the main context for coordination only.
- Fix tasks from a gate (`type: fix`) are one round: implement all of them, then hand over to `qa` once. Never deploy, start a preview or re-run auditors between fix tasks (`conventions.md` §12).

## Stop conditions and report
Before `skill_end`, run `python3 -I "${CLAUDE_SKILL_DIR}/../core/scripts/dev_cost.py" --root "${CLAUDE_PROJECT_DIR}" ingest` (token usage per stage, `conventions.md` §14).
Stop when: requested tasks done; milestone complete (announce the gate); an `always_ask` question with action `ask` cannot be deferred; three consecutive tasks blocked (environment problem; `pause_policy.blocked_env`). Always end with: tasks completed (ids + SHAs), tasks blocked (reasons), decisions taken (ADR ids), open questions added, and the next command.

## Never
- Never skip or weaken tests to pass; never commit with failing tests; never edit `state.json` manually; never push unless `may_push` is true and the brief asked for it.

**Last line** (`conventions.md` §15): end the final report with the next command alone on the last line, written in full: `/dev-kit:qa M1` when the milestone is complete, otherwise `/dev-kit:implement`. Claude Code then offers it as the greyed-out prompt suggestion (Tab or Right arrow).

## Existing projects (brownfield)

When state has `brownfield` (`conventions.md` §16): follow the folder layout, test framework, test location and naming, and the build/test/lint commands in `.dev/discovery.md` §3–4 (they override `test-pyramid.md` defaults and `architecture.md` §8 where they differ); never add a runner, linter, formatter or build tool without an `always_ask` decision. Uncommitted changes that belong to no task are the user's work: always ask (never stash them on your own). In `maintenance` mode the tasks come from `issue` in the open maintenance milestone (`M<n> — Maintenance`, numbered from `brownfield.first_milestone`); when its tasks are done, the milestone goes to `qa M<n>` like any other, and new issues then open `M<n+1> — Maintenance`. With no task at all, suggest `/dev-kit:issue`.
